# Speed Sync SQL 总体产品方案

状态：总体方案已由用户确认。本文描述未来产品；本次 change 只交付规划与设计，不实施以下功能。文中建议作为后续分阶段开发的规划依据，具体技术承诺仍须验证。

## 1. 目标与使用场景

为 Windows、macOS 内部用户提供一个围绕单表的 MySQL 比对与同步工作台：选好两端、看清差异、选择同步范围、预览并执行、复核结果。

典型场景为开发环境与测试环境之间补齐字段、检查索引和触发器差异、同步字典或配置表数据。这些是设计场景，不代表已收集到真实用户数据。

成功标准：用户能始终回答“比较的是哪两张表”“这次改哪一端”“会新增、修改、删除什么”“哪里成功，哪里没执行”。视觉应有完成度，操作应少跳转，不需要为了常见任务手工拼 SQL。

## 3. 产品结构

产品包含“比对工作台”“连接管理”“执行记录”“设置”四个一级入口。启动优先恢复最近使用的连接选择和布局，不自动连接后执行任务。没有历史时直接在工作台引导添加两端连接。

工作台有“结构”“数据”两个主标签；连接、表配对和方向共用，两个标签的变更计划分别管理。先做结构变更后，原有数据计划作废并重新比对。

```mermaid
flowchart LR
    C[选择左右连接与数据库] --> T[配对一张表]
    T --> S[结构比对]
    T --> D[数据比对]
    S --> SP[选择对象与方向]
    D --> DP[选择匹配键、范围与模式]
    SP --> P[预览同步计划]
    DP --> P
    P --> E[执行并记录结果]
    E --> R[重新比对受影响范围]
    R --> S
    R --> D
```

## 5. 结构同步的产品规则

### 5.1 “双向”与“替换”

两端在界面固定称为左侧和右侧。选择“左 → 右”时左侧是读取基准，右侧是写入端；反向则相反。不同对象可分多次向不同方向同步，但同一计划不混合两个写入端。

“同步选中对象”只影响选中项及已明确列出的必要依赖；“整表结构对齐”会列出所有新增、修改和删除，由预览给出完整结果。均不默认 DROP TABLE 后重建，不承诺结构修改不会影响既有数据。

不同名表配对保留写入端现有表名。仅读取端存在时可生成目标建表计划；仅写入端存在时不把“读取端缺失”解释为自动删除整表。整表删除不纳入快捷同步。

### 5.2 有用的差异与噪声

- 表、字段按实际标识符规则匹配，不擅自统一大小写；人工确认映射优于猜测重命名。
- 结构化元数据为主，原始 DDL 作为依据与详情；不能仅以 DDL 文本不同判定结构不同。
- 空白格式、数据库名称等环境差异单独处理；字符串内容和表达式不能粗暴去空格或转小写。
- AUTO_INCREMENT 当前计数不默认当作结构差异；字段是否自增仍比较。
- 不把未读到、无权限、版本不支持误报成“该对象不存在”或“完全相同”。

### 5.3 依赖与能力分级

计划应解释字段、索引和约束的关联。必要附加操作显示为“关联操作”，不得暗中扩大选区。外部表依赖可以检测和提示，本工具不自动改写其他表来强行通过。

普通字段/索引/主键、常规表属性、基本触发器为核心自动同步目标。外键/CHECK、生成列、函数索引、分区、引擎转换和跨版本语法按后续验证分级为“可自动执行”“需处理条件”“仅展示”。不支持的对象保留可读定义，不输出貌似有效的替代 SQL。

触发器替换须处理原定义、上下文与创建权限。DEFINER 不默默删去或替换；可保留原定义，或由用户明确选择写入连接用户并显示行为变化。触发器正文中的其他表/库引用不自动全文替换。

## 6. 数据同步的产品规则

### 6.1 前提

结构不必逐字一致，但参与写入的字段、必填列、生成列、键和值类型必须兼容。无法兼容时先引导处理结构，再重新生成数据计划。

更新和删除需要稳定、唯一的匹配键。优先主键，其次两端已验证的非空唯一键，可用复合键。没有可靠键时允许浏览，禁用自动合并和完全对齐；不把物理行顺序当作身份，不在首期增加无键表猜测匹配。

目标为空且字段兼容时可单独规划整表导入能力，但无键表复制、清空后重灌均不作为本轮总体核心承诺，后续有真实需求再单独设计。

### 6.2 三种模式

| 模式 | 新增 | 更新同键记录 | 删除目标独有记录 | 适用场景 |
| --- | --- | --- | --- | --- |
| 补齐缺失记录 | 是 | 否 | 否 | 补配置、补字典项 |
| 合并更新 | 是 | 是 | 否 | 把指定字段更新到另一环境 |
| 完全对齐 | 是 | 是 | 是，限已确认范围 | 明确要求目标集合与基准一致 |

默认选补齐缺失记录。更新字段可选；主键不作为普通值批量修改。冲突不由“较新时间戳”自动裁决，也不做持续双向复制。

### 6.3 筛选与完全对齐

采用共享的逻辑筛选条件，经字段映射后应用于两端。仅完全扫描完成后才能把缺失判为不存在；中断、抽样与当前分页不能作为删除依据。

筛选范围外的目标记录必须保留。若读取范围内的键与目标范围外的同键记录冲突，列为“范围外同键冲突”，不自动更新或删除该记录。外键引用造成删除失败时停止并解释，不自动关闭外键检查。

### 6.4 精度、一致性与规模

- BIGINT、DECIMAL 以无损表示跨桥传递；NULL、空串、0 分开；二进制、时间、JSON 等按类型比较。
- 不用屏幕上截断的文本参与比较。超长字段和 BLOB 详情按需加载；相同哈希不能成为唯一的确定相同依据。
- 数据可能在扫描后被其他程序更新。预览标明读取时间；写入前检查目标旧值或等价并发条件，冲突停止并重新比对。
- 两台服务器的读取快照不能直接视为同一瞬间；持续写入环境下不承诺全局瞬时一致。需要静态一致时建议用户安排安静时段。
- 大表分批读取、后端比较，前端只展示分页结果；不把整表经 WebChannel 传给 React。
- 先展示扫描量与阶段，确知总量才显示百分比；数值来自实际任务，不承诺尚未测量的吞吐和耗时。

### 6.5 执行结果

数据变更遵守当前表事务能力，优先验证 InnoDB。分批提交意味着前面已提交批次不会因后续失败整体撤销。停止请求在可控边界生效，不承诺中断正在执行的服务器语句。

连接中断且无法确认提交结果时显示“结果待核实”，先重新读取目标状态，禁止盲目重试。目标触发器照常可能执行；默认不禁用触发器，预览提示存在触发器及副作用边界。最终复核报告的是复核时刻的状态，不把扫描后的并发变化隐藏为成功。

## 7. 必要防护的上限

只保留写入端标识、SQL/操作预览、删除与缩窄类型提醒、计划过期检测、基础凭据保护和执行记录。不做角色体系、审批中心、团队权限、合规审计平台。

密码不进入日志与普通配置；默认会话内使用，“记住密码”交由系统凭据存储。普通保存布局等操作不弹确认。真正执行时只用一次摘要确认，破坏性条目在同一处突出，不连续堆叠多层弹窗。

## 8. 总体非目标

PostgreSQL/SQL Server/MariaDB 兼容承诺、整库迁移、定时或实时复制、任意 SQL IDE、数据清洗脚本、跨库 ETL、自动推断业务键/重命名、无条件在线无锁变更、完整备份恢复系统。视图、存储过程、函数和事件属于数据库级对象，暂不纳入单表核心同步。
