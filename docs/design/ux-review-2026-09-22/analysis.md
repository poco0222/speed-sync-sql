# Speed Sync SQL 体验优化分析

日期：2026-09-22。范围：产品探索与设计审查；未修改业务代码、未连接真实数据库、未执行同步。

## 判断

核心能力已经覆盖从比对到同步。下一轮应让用户更快看懂差异、明确写入范围、复用上次配置、完成结果复核。继续堆功能的收益尚无证据。

四个目标分别是：交互上明确下一步；可读性上优先看到变化；便利性上减少重复配置；用户黏性上让下次同类任务更省事。内部工具不宜用使用时长、每日打开次数或通知数量衡量黏性。

目标用户暂按“有基本数据库知识、反复核验两端库表的内部人员”假设。实际使用频率、表规模、岗位与当前耗时尚无用户研究，不把推断当成已证实需求。

## 具体发现

### F1 · P2：数据页无法展开已收起的库表导航

当前可复现：在结构页收起导航后切换到数据页，导航和展开按钮都不可见，需要返回结构页恢复。

依据：`frontend/src/SchemaWorkbench.tsx:113` 的开关处在仅结构模式显示的 toolbar，114–115 行控制共享导航。

建议：将开关移至两种模式共用的位置；保持状态一致。属于局部小修，可先于大布局改进。

### F2 · P2：结构属性展示掩盖真正变化

依据：`SchemaWorkbench.tsx:137` 列表展示完整属性；`frontend/src/style.css:67` 的 `.property-preview` 限高 155px 且可滚动。左右单元格独立滚动，容易失去对照位置。

建议：差异行默认仅显示变化属性；新增/缺失对象显示关键属性摘要，完整内容在展开区。保留文本标签，不只靠颜色。

### F3 · P2：结果在配置与技术说明之后，阅读路径过长

依据：`frontend/src/DataWorkbench.tsx:39–48`。字段、范围、扫描阶段、批次、两侧时间戳和一致性说明排在结果表前。历史 1440×900 截图中，结果表接近视口底部。

建议：比对后将配置折叠成可编辑摘要；顶部显示结论、范围、差异计数。详细时间与快照信息按需展开，不能隐藏影响判断的未完成、删除和分批提交风险。

### F4 · P2：历史数据任务的复核仍需重新准备上下文

依据：`frontend/src/SyncRecords.tsx:24` 明确要求返回后选择数据比对、重新读取键字段、确认范围；`frontend/src/main.tsx:127` 的恢复回调仅恢复 state、重建工作台。当前没有实测完整记录恢复流程。

建议：先让数据记录直接进入数据模式。完整方案恢复可验证的配置草稿，重新读取后确认字段与条件；不能恢复时明确缺失项，不悄悄扩大到全表，不重放历史计划。

### F5 · P3：准备阶段提前出现大量写入决策

依据：`DataWorkbench.tsx:49` 始终挂载 DataMergePanel；未读取时已显示方向、模式和写入说明。浏览器空状态可见。

建议：准备阶段只显示“完成比对后可预览写入”；可靠键比对完成后再展开模式选择。完全对齐仍需明确删除数量和整行删除语义。

补充设计风险：扫描范围、页面筛选、写入范围存在不同语义。当前文案已有提醒，问题是用户是否读到并理解；没有证据证明发生过误写。应通过布局和理解测试验证，而不是删除现有防护。

## 建议优先实施的五项

### 1. 范围说清楚：当前查看不等于实际写入

把“比对条件”和“查看结果”分成不同区域，预览入口旁明确目标、模式及实际增改删数量；数字只有在有效计划生成后才当作可执行计数。

- 入选原因：直接服务交互理解与控制。Jev 第一；当前已有文字提示，调整层级可先做小范围版本。
- 可行性：中等；先改呈现，不改变现有后端选择与执行规则。
- 差异化价值：使这个单表同步工具的影响范围容易解释，属于潜在体验优势；未做竞品研究。
- 待验证假设：用户会把“仅显示某种差异”误解为“只写入当前列表”。
- 验证：在有状态过滤、键定位、分页及共享条件的原型中，让用户先说出将写入哪些记录、会否删除，再看预览。对比现版正确率与犹豫点，错误未消除前不减少确认。

### 2. 先看到变化：结果成为工作台主体

比对完成后收起配置为摘要；结构只突出变化属性，数据保留左右原值详情入口，技术时间与一致性详情按需展开。

- 入选原因：当前截图与源码都有直接证据；改善可读性，也是核心价值交付。D1 与 D4 合并成同一个成果，避免分开重复建设。
- 可行性：中等，以前端布局及展示规则为主；不同、缺失、未读取状态必须分别保留。
- 差异化价值：让用户快速解释“哪里不同”，契合对照工作台的已选方向。
- 待验证假设：多数任务首先查变化，不需要逐行阅读全部相同属性。
- 验证：让用户找出三个指定变化并解释左右差别，比较耗时、滚动次数和漏看情况；同时检查完整属性仍可到达。

### 3. 常用任务：下次直接恢复配置

保存命名任务，包含两端对象与比对配置；最近使用作为同一入口，恢复后重新读取、校验，不恢复有效旧结果或旧写入计划。

- 入选原因：同时改善便利性与复用意愿。P1、P2、E4 是同一价值链，不做三个独立系统。
- 可行性：中等，需要持久化契约、失效校验和配置迁移；先单任务收藏，不做复杂项目管理。
- 差异化价值：降低重复任务准备成本，不靠无意义提醒维持打开次数。
- 待验证假设：用户反复比对同一组连接、表和范围，且频率足够高。
- 验证：先收集实际重复任务频率；让同一用户跨两次任务恢复配置，对比手工输入次数与完成时间。字段被删、连接变更时不能自动退回全表范围。

### 4. 固定任务上下文与下一步操作

合并冗余连接信息，目标、方向与任务状态固定可见；数据页与结构页共用导航开关，预览与执行按阶段出现。

- 入选原因：包含已复现的小问题，且可减少长页来回滚动；与范围表达共用上下文条，但负责操作位置而非范围语义。
- 可行性：导航修复低；固定操作区中等。保留现有锁定、停止与确认机制。
- 差异化价值：长任务中持续知道“对谁做什么”，不是单纯美化顶栏。
- 待验证假设：长页让用户丢失目标或找不到当前下一步。
- 验证：1440×900、1024×768 下切换模式、收起导航、滚动至详情，再尝试预览；目标与恢复入口都应可见。后续再验证键盘全流程。

### 5. 复核闭环：知道是否真的完成

执行后同时呈现“哪些批次已提交”和“重新比对后的当前差异”；从记录返回时恢复对应模式与可用配置草稿。

- 入选原因：完善结束体验，强化信任。当前已有复核入口，应补足上下文与解释，而不是重建历史系统。
- 可行性：中等；区分当前会话已有配置和历史记录缺失字段。不能以状态文案替代真实重新读取。
- 差异化价值：结果可解释、可追踪，是再次使用的理由。
- 待验证假设：用户会把执行成功视作两端完全一致，或因复核准备繁琐而跳过。
- 验证：覆盖补齐后仍有差异、合并后保留目标独有、部分失败、待核实四种情境，让用户正确解释已提交与未确定部分。

排序说明：Jev 原始前五为 D3、P1、E2、D2、P3。最终提升 D1，是因为本地证据直接支持差异阅读问题；E2 快捷操作虽得分较高，使用频率与真实键盘流程尚未验证，先后置。分数差距小且置信度有限，不能机械取前五。
